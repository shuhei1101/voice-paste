# 構造の決定

## 決定

| 決めること | 決定 | 理由 | 採らなかった案 | 補足 |
| --- | --- | --- | --- | --- |
| 責務とサービスの境界 | 1 つの常駐サービスにし、中を変更の理由が異なる責務で分ける<br>・セッション（録音・文字起こし・出力の状態の遷移と、同時に 1 つだけ動かす排他）<br>・録音（マイク・システム音量）<br>・文字起こし（エンジンのインターフェースと、ローカルの Whisper・OpenAI の実装）<br>・補正（用語集）<br>・出力先（貼り付けて送信・貼り付けのみ・コピーのみ・AI チャットへ送る・呼び出し元のエンドポイントへ返す）<br>・履歴<br>・入口（API・ホットキー・トレイ・画面） | 入口が増えても録音から出力までの流れは 1 つで、セッションが排他を持てば API とホットキーがぶつからない。境界が見えるまでは単一の構成から始める（MonolithFirst） | ・録音・文字起こしを別のサービス（別の HTTP サーバー）に分ける: 状態と排他をサービス間で合わせることになり、1 人で運用する量に見合わない<br>・今の `main.py` の一続きの流れを残して API を足す: 貼り付けを外せず目的 1 を満たせない | 品質シナリオ 1・5・6。機能の扱いの「常駐して起動する」「録音」「出力先」 |
| リポジトリとプロセス | リポジトリは今の 1 つ。プロセスは常駐サービス 1 つと、文字起こしワーカーの子プロセス（残す）。常駐サービスの中は、画面のメインスレッド・API のサーバーのスレッド・ホットキーのスレッドに分ける | 同時に変わり同時に動かすものは同じ場所に置く。ワーカーを子プロセスに隔離した形は CUDA のクラッシュから常駐を守る | ・API のサーバーを別のプロセスにする: 画面とセッションの状態をプロセス間で渡すことになる<br>・ワーカーを同じプロセスに戻す: CUDA のクラッシュで常駐ごと落ちる | 品質シナリオ 4。機能の扱いの「ローカルの Whisper での文字起こし」 |
| モジュール構成（ルート直下を含む） | コーディング規約『レイアウト』の機能フォルダ型にする（`src/voice_paste/` の下）<br>・`main.py`: 配線（composition root）<br>・`shared/`: ログ・設定のモデル・例外・共通の型・置き場所のパス<br>・`features/`: `session`（状態の遷移と排他・録音から出力までの流れ）・`recording`・`transcription`・`correction`・`outputs`（出力先ごとにサブフォルダ）・`history`<br>・`integrations/`: `whisper`（文字起こしワーカーの子プロセス）・`openai`・`volume`（pycaw のアダプタ）・`keyboard`（貼り付けとクリップボード）<br>・`runtime/`: `hotkey`（グローバルのホットキーの受付）<br>・`server/`: FastAPI の app と middleware（route は `features/session/route.py`）<br>・`ui/`: PySide6 の画面とトレイ（規約に画面の置き場所が無いため、`server/` と同じ入口として足す）<br>依存の向きは規約『依存関係管理』のとおり `features`・`server`・`ui` → `integrations`・`runtime` → `shared` とし、`features` どうしは import しない。`session` はほかの feature を自分の `types.py` の型（Protocol）越しに受け取り、`main.py` で配線する<br>ルート直下は `pyproject.toml`・起動のバッチファイル 1 つ・`settings.sample.toml`・`README.md`・`CLAUDE.md`・`src/`・`resources/`・`tests/`・`dev/`・`docs/` に絞る | ユーザーの回答でコーディング規約のレイアウトに合わせる。責務の境界と依存の向きがフォルダの並びから読め、出力先の追加が `features/outputs` の中で閉じる | ・`voice_paste/` の直下に責務ごとのパッケージを並べる（`session`・`audio`・`api` など）: コーディング規約のレイアウトと揃わない<br>・層（画面・サービス・データ）で分ける: 出力先を 1 つ足すと層をまたいで直すことになる<br>・今の平らな並び（`main.py`・`gui.py`・`settings_gui.py`）のまま: 責務の混在が残る | 品質シナリオ 5。機能の扱いの「配布用のビルド」「プロンプトのファイル」を捨てることで `setup/` のビルドと置き場所が消える |
| 設定とデータの置き場所 | 設定は TOML の 1 ファイル（`%APPDATA%\voice-paste\settings.toml`）に持ち、pydantic のモデルで検証し、tomlkit でコメントを保ったまま書き戻す。出力先は一覧で持ち、出力先ごとにオン・オフを持つ。項目ごとに再起動が要るかの印を持つ<br>履歴・ログ・一時の音声は `%LOCALAPPDATA%\voice-paste\` の下に置き、保持期間を過ぎたものを消す<br>今の `.env` は起動を新しい構成へ切り替えるときに 1 度だけ TOML へ移し、`.env.migrated` に改名して残す（リスクと移行計画の回答で時点を変えた） | 番号付きのキー（`AI_SEND_{n}_*`）をやめて一覧で持てる。値を確かめてから書くため、設定画面の保存で起動できなくなるリスクを消せる。置き場所を Windows の慣習（platformdirs）に合わせ、秘密の値（API キー）が git の管理下に入らない | ・`.env` のまま: 番号付きのキーが残り、#5 の送り先が増えるほどキーが増える<br>・YAML: 書き戻すとコメントが消え、暗黙の型変換が起きる<br>・リポジトリの直下に置く: API キーが git の管理下に入る恐れがある | 機能の扱いの「設定画面」「AI チャットへ送る（オン・オフ）」「古いログの削除」「履歴への保存」 |
| 依存の見直しと新しい技術 | 採用（新しく入れる）:<br>・FastAPI と uvicorn: API のサーバー（品質シナリオ 1・6）<br>・httpx: 呼び出し元のエンドポイントへの返送（品質シナリオ 1）<br>・import-linter: 依存の向きの検査（品質シナリオ 5）<br>・pydantic・tomlkit・platformdirs: 設定の検証・書き戻し・置き場所。品質シナリオには当たらず、機能の扱いの「設定画面」（値を確かめてから書く）と目的 2（設定を 1 か所で変える）に応える<br>・PySide6（`pyside6-essentials`）: 画面とトレイ。品質シナリオには当たらず（インタラクション容易性は重要度 中）、目的 3（画面の見た目・画面構成）と機能の扱いの「録音」「設定画面」「トレイのメニュー」に応える<br>採用（今の依存を使い続ける）:<br>・faster-whisper・openai: 文字起こしのエンジン（品質シナリオ 2・4）<br>・sounddevice・numpy・scipy: 録音と音声ファイル（品質シナリオ 1・3）<br>・pynput: グローバルのホットキー（品質シナリオ 3・6）<br>・pyperclip: 貼り付けとコピーの出力先（品質シナリオ 3）<br>・pycaw と comtypes: システム音量の操作。版を `==` で固定し、自前のアダプタで包む（品質シナリオ 7）<br>試す:<br>・python-dotenv: 今の `.env` を TOML へ移す処理でだけ使い、移行の処理と一緒に消す<br>様子見:<br>・pydantic-settings: 環境変数で設定を上書きしたくなったら<br>採らない:<br>・tkinter・pystray（PySide6 に置き換える）・PyInstaller（配布用のビルドを捨てる）・CustomTkinter・Flet・pywebview | FastAPI は検証と OpenAPI を持ち、pydantic・httpx は openai の依存として既に入っている。PySide6 はテーマ（QSS）・トレイ・最前面・カーソルのあるモニターへの表示を 1 つで持ち、pystray と Win32 の直呼びを外せる | ・tkinter に ttkbootstrap を足す: テーマは ttk の部品にしか効かず、トレイとモニターの判定は自前のまま<br>・標準の `http.server`: 検証・OpenAPI・非同期の返送をすべて手で書く<br>・comtypes で音量を直に呼ぶ: pycaw の中身の写しを自分で持つことになる | 振り分けは調べたことの Tech Radar の Adopt（採用）・Trial（試す）・Assess（様子見）・Caution（採らない）に合わせた。目的と制約の「外せる制約」 |
| 横断の方針 | ・ログ: 標準の logging 1 本にまとめ、日付ごとのファイルに書き、保持期間で消す。uvicorn のログもアプリのロガーへ寄せる<br>・エラー: 起動の失敗はトレイで知らせてログに残す。API は例外を HTTP のエラー（処理中は 409）に変える。文字起こしの失敗でも録音は残す<br>・スレッド: 画面の操作はメインスレッドだけで行い、ほかのスレッドからは Qt の Signal で渡す<br>・API の守り: 127.0.0.1 だけで待ち受け、Host を確かめ、Origin の付いた要求（ブラウザから）を拒み、起動ごとに作るトークンで照合する<br>・返送: 送り先は loopback と設定で許可したホストに限り、タイムアウトと回数を決めて再送する | 全体に効く方針を 1 か所に決め、モジュールごとに書き分けない。API はマイクを起動できるため、ブラウザからの CSRF と DNS rebinding を防ぐ | ・API に認証を付けない: 同じ端末のブラウザのページから録音を始められてしまう<br>・画面の部品を各スレッドから直に触る: tkinter で今の `after` の書き分けが要ったのと同じ問題が残る | 品質シナリオ 3・4・6。セキュリティ（重要度 中）は待ち受けを端末の中に限る形で扱う（品質目標の回答）。返送のタイムアウトと回数は PoC で決める |
| 画面 | 画面の構成・見た目・項目の並び（設定画面のタブ・トレイのメニューのまとまりを含む）は、作り直しのデザインの工程（デザインスタイル選定・画面一覧・画面遷移・モック作成）で designer に任せる<br>構造として決めるのは次だけにする<br>・画面とトレイは PySide6 で作り、`ui/` に置く。画面は入口として `session` を呼び、録音や文字起こしを直に触らない<br>・設定画面の欄は設定のモデルから組み立てる（項目を足しても画面の直しが増えない）<br>・designer に渡す要件: 画面は録音の画面・文字起こし中の表示・設定画面・トレイのメニュー・ダイアログ（処理中に開始が来た・起動に失敗した）。設定ファイルの項目は全て画面で変えられる。録音の画面は表示中も最前面を保つ（[#4](https://github.com/shuhei1101/voice-paste/issues/4)） | ユーザーの回答で画面系は designer に任せる。目的 3 の見た目・画面構成はデザインの工程で決め、構造では画面を入口の 1 つに閉じ込める | ・構造の決定で設定画面のタブ・トレイのメニューの並びまで決める: 画面系を designer に任せる回答と合わない<br>・よく変える項目だけ画面に載せ、残りは TOML を直に書く: 設定ファイルを直に書く手作業が形を変えて残る | 機能の扱いの「録音」「文字起こし中の表示」「設定画面」「トレイのメニュー」 |
| テスト | ・特性テスト: 作り直しの前に、用語集の補正の入出力と、刷新前に録った音声の文字起こしの結果を期待値として固める<br>・構造の検査（fitness function）: import-linter で依存の向き（コーディング規約『依存関係管理』の層の向き・`features` どうしが import しない・出力先どうしが import しない）を検査する<br>・契約テスト: 音量のアダプタを Windows の実機で検査し、依存の版を上げたら回す<br>・結合テスト: API の開始 → 停止 → 完了 → 返送と、処理中の開始が 409 になることを確かめる<br>・既存の `tests/` は捨てる | 品質シナリオ 2（文字が変わらない）・5（出力先の追加が 1 か所）・7（版の変化を検知する）を、テストで守れる形にする | ・特性テストを作らずに作り直す: 刷新の前後で文字が変わっても気づけない<br>・既存のテストを直して残す: 作り直しで実装が変わり、再び合わなくなる | 品質シナリオ 1・2・5・6・7。機能の扱いの「既存のテスト」 |

## 調べたこと

| 題材 | 分かったこと | 出典 | 補足 |
| --- | --- | --- | --- |
| MonolithFirst | 境界が正しいかは作ってみないと分からないので、まず単一の構成で作り、分けるのは境界が見えてから | [MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html) | 1 つの常駐サービスにし、中をパッケージで分けた |
| 12-Factor / XDG Base Directory | 環境ごとに変わる値はコードから分ける。置き場所は設定・データ・状態・キャッシュで分け、Windows では `%APPDATA%`・`%LOCALAPPDATA%` が慣習（platformdirs が対応する） | [The Twelve-Factor App: Config](https://12factor.net/config)・[XDG Base Directory](https://specifications.freedesktop.org/basedir/latest/)・[KNOWNFOLDERID](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid) | 設定を `%APPDATA%`、履歴・ログ・一時の音声を `%LOCALAPPDATA%` に置いた |
| Tech Radar | 技術を Adopt（採用）・Trial（試す）・Assess（様子見）・Caution（採らない。旧 Hold）に振り分ける | [Tech Radar FAQ](https://www.thoughtworks.com/radar/faq)・[Build Your Own Radar](https://github.com/thoughtworks/build-your-own-radar) | 依存の見直しの行を、採用・続けて使う・様子見・採らないで書いた |
| arc42 の横断の方針 | ログ・エラー処理・認証など複数の部品にまたがる方針を 1 か所にまとめ、各部品で繰り返さない | [arc42 Section 8](https://docs.arc42.org/section-8/) | 横断の方針の行 |
| ADR / MADR | 決定ごとに背景・決定・検討した案・結果を残し、考えを変えたら古い記録を消さずに置き換える | [Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)・[MADR](https://adr.github.io/madr/) | 決定の表に理由と採らなかった案を必ず書いた |
| 特性テストと fitness function | 特性テストは今の振る舞いをそのまま期待値にして固める安全網。fitness function はアーキテクチャの目標を継続して検査する仕組み。Python では import-linter で import の向きを検査できる | [Characterization Testing](https://michaelfeathers.silvrback.com/characterization-testing)・[Fitness function-driven development](https://www.thoughtworks.com/insights/articles/fitness-function-driven-development)・[import-linter](https://import-linter.readthedocs.io/en/stable/) | テストの行 |
| 画面のライブラリ | PySide6 は QSS でテーマをまとめられ、`QSystemTrayIcon`・最前面・`screenAt` でトレイとモニターの判定まで持つ。`pyside6-essentials` だけなら wheel は約 78 MB、ライセンスは LGPL-3.0 | [Qt for Python のライセンス](https://doc.qt.io/qtforpython-6/licenses.html) | CustomTkinter・Flet・pywebview・ttkbootstrap と比べた。Flet と pywebview はトレイを持たない |
| API のサーバー | uvicorn の `Server.serve()` は専用のスレッドのイベントループで動かせ、`should_exit` で止められる。ローカルの API は Origin の確認・127.0.0.1 での待ち受け・認証で DNS rebinding を防ぐ | [uvicorn server.py](https://raw.githubusercontent.com/Kludex/uvicorn/main/uvicorn/server.py)・[MCP の Transports（Security Warning）](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)・[Starlette Middleware](https://raw.githubusercontent.com/Kludex/starlette/main/docs/middleware.md) | 待ち受けに失敗すると uvicorn はスレッドを黙って終えるため、起動後に `server.started` を確かめる |
| 設定の持ち方とシステム音量の操作 | tomli-w は書き戻すとコメントが消え、tomlkit は保てる。pycaw は日付の版で API が変わるため `==` で固定し、自前のアダプタに対して契約テストを置く | [tomli-w の FAQ](https://github.com/hukkin/tomli-w#does-tomli-w-support-writing-documents-with-comments)・[pycaw の CHANGELOG](https://github.com/AndreMiras/pycaw/blob/main/CHANGELOG.md) | 今の `pyproject.toml` の `pycaw>=20220416` は下限しかない |
