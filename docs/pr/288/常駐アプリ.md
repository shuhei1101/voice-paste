## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 原因の特定 | 取り消しの経路で画面のスレッドを止めうる処理を、ログと実機の計測で調べた。1 つに特定できなかったため、どれが原因でも画面のスレッドが止まらない対策にする | 報告の時刻（2026-11-13 00:55〜00:58 JST）の常駐アプリのログでは、取り消しは全て「録音を捨てた」「録音を取り消した」まで警告なしで進んでおり、止まった箇所はログに出ていない。報告者の端末（既定の入力: Razer Seiren V3 Mini・MME）での計測では、マイクの入力を開いた直後〜1.5 秒後に止めて閉じるまでが 0.04〜0.14 秒、音量のエンドポイントを開いて読むまでが 0.02 秒で、単独では長く止まらない。画面のスレッドで動く取り消し（`SessionManager.cancel`）は、ほかのスレッドの開始が録音セッションのロックを持つ間（初回のマイクを開く処理は 0.5 秒）の待ち、マイクの入力を閉じる処理、音量のフェードの終わりの待ち（最大 1.0 秒の `FADE_JOIN_TIMEOUT_SEC`）を、全て画面のスレッドで待つ |
| 開始と取り消しの重なり | 録音の画面からの取り消し（`UiDeps.cancel`）を、別のスレッドで動かす `cancel_in_background`（`main.py`）で始め、画面のスレッドは取り消しの終わりを待たない。開始と取り消しは今までどおり録音セッションのロックで 1 つずつ動き、取り消しは開始が終わるのを待ってから録音を捨てる | [要件](./要件.md) の対策の案 A。`SessionManager` の状態の遷移は変えない。取り消しの処理の間に届いた録音開始のホットキーは、取り消しが終わってから録音を始める |
| 終了の処理の間の開始 | 終了の処理の間に録音を始める操作を受けたら、終了の処理中で今は録音を始められないことを示す | 処理中のダイアログで示す（[確認ログ](./確認ログ.yaml)）。`start_local_session` が断られた理由（今の録音セッションの入口）を busy の通知の detail（`BUSY_REASON_API` / `BUSY_REASON_FINISHING`）にし、`UiController` から `show_busy_dialog` へ引き渡す |
| 処理中のダイアログ | 断った理由（API の録音の処理中・終了の処理中）ごとに本文を分ける | 終了の処理中の本文は「前の録音を文字に起こして届けています。終わってから、もう一度録音開始のホットキーを押してください。」 |
| 回帰のテスト | `cancel_in_background` の単体テスト（取り消しの終わりを待たずに戻る）、`start_local_session` の単体テスト（断った理由ごとの detail）、処理中のダイアログの結合テスト（終了の処理中の本文）を追加する | 開始の直後の取り消しは E2E（SC-8 の `正常シナリオ（開始の直後に取り消す）`）で、画面のスレッドが 0.5 秒以内にイベントを処理することを確認する |
