## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| タグの語彙 | 記載の前に `search_docs` の `group_by: tags`（`source: "*"`）で使用されているタグを検索し、knowledge・AI Monitor と同じ意味のタグを再利用する。付けるかは判定フローチャート『タグの付与』で決める | 例: 録音セッションの設計書に `topic:録音`・`action:録音`、faster-whisper に `tool:faster-whisper` |
| `main: true` | 設計書ごとに最も分量の多い主題のタグ 1 つに付ける | - |
| `aliases` | 用語集の用語・本文や会話で設計書を指す別の名前を、判定フローチャート『エイリアスの登録』で決めて記載する | 別の名前が無い設計書には記載しない |
| `lead` | 「何を定め（受け持ち）、どんなときに参照するか」の 1 文にする。持たない設計書は新規に記載し、持つ設計書は中身を変えずに記載方法だけを統一する | モジュール構成は受け持つ処理、外部ライブラリは使用する部分を主語にする |
| サブシステムをまたぐ設計書 | アーキテクチャ図・非機能要件・テスト実行方法・開発コマンド・フォルダ構成は、この計画書で扱う | - |
| `files.yml` の行 | `tags` は行の `related` が指す設計書のタグから、そのファイルが受け持つ主題を選ぶ。`description` は「何を受け持ち、どんなときに参照するか」の 1 文にする | テストの行は検証する対象を受け持ちとして記載する |
| 書き込みの手段 | 設計書は project-index の `write_docs`（`set`・`text_edits`）で書き込み、`files.yml` は Edit で書き換える | 検査に通らなければ書き込まれない |
| 確認 | 設計書の検証のコマンド（`PYTHONPATH=src uv run python -m ai_monitor.design_docs validate --root {worktree}`）と、project-index の `describe` の警告で、追加したキーによる違反が無いことを確認する | - |
