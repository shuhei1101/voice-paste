## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 原因の特定 | 再現と原因の特定は行わない（利用者の判断） | 調べた範囲: 報告の時刻（2026-11-13 00:55〜00:58 JST）の Windows のログでは、開始と取り消しは重なっていない（開始から取り消しまで 1.37 秒・1.66 秒）。報告者の Windows の端末での計測では、マイクの入力を開いた直後に止めて閉じるまでが 0.04〜0.14 秒、音量のエンドポイントを開いて読むまでが 0.02 秒。事象は Linux でエンジンが OpenAI API のときに起きていた（利用者）。a5 の Hyper-V の Ubuntu（Xorg）で、エンジンを local_whisper・OpenAI API にして開始の 0.0〜1.5 秒後の「×」を 30 回あまり試したが、録音の画面が出た後の取り消しは全て 0.2 秒以内に閉じた |
| 開始の直後の取り消しの猶予 | ホットキー・トレイの録音を、始めてから `recording.cancel_grace_sec` の秒数の間に取り消したら、録音の画面だけを閉じ、内部の録音は続ける。始めてから猶予の秒数が経った時点で、新しいスレッドで録音を捨てて待機中に戻す。猶予の後の取り消しは、新しいスレッドでその場で捨てる | 猶予の間は、取り消した録音を確定・一時停止・録音の画面に戻す操作を受け付けず、再起動・終了は内部の録音を捨ててすぐ行う。処理中のダイアログの理由の判定（`start_local_session`）は、猶予の間の録音を終了の処理中として扱わない。猶予の間の録音開始は内部の録音を引き継いで音と経過時間を 0 に戻し、API の開始は内部の録音を捨ててから始め、猶予は全ての取り消しの操作に適用し、猶予の間のトレイは待機中に見せ、音量は取り消した時点で戻して始め直したら下げ直す（[確認ログ](./確認ログ.yaml)）。`SessionManager` の状態と遷移の詳細はモジュール構成設計で決める |
| 猶予の秒数の設定 | `recording.cancel_grace_sec`（秒・0 以上・既定 5.0。0 は猶予を持たない）を設定のモデル・既定値・設定の設計書に追加し、設定画面の録音のまとまりに入力欄を追加する | 設定画面の入力欄の見た目はモック作成で確認する |
| 取り消しで画面のスレッドを止めない | 録音の画面からの取り消しは、取り消しを新しいスレッドで始めて終わりを待たない | 取り消しのホットキーも同じく猶予を適用し、取り消しの処理を新しいスレッドで動かす |
| 終了の処理の間の開始 | 終了の処理の間に録音を始める操作を受けたら、終了の処理中で今は録音を始められないことを示す | 処理中のダイアログで示す（[確認ログ](./確認ログ.yaml)）。`start_local_session` が断られた理由（今の録音セッションの入口）を busy の通知の detail（`BUSY_REASON_API` / `BUSY_REASON_FINISHING`）にし、`UiController` から `show_busy_dialog` へ引き渡す |
| 処理中のダイアログ | 断った理由（API の録音の処理中・終了の処理中）ごとに本文を分ける | 終了の処理中の本文は「前の録音を文字に起こして届けています。終わってから、もう一度録音開始のホットキーを押してください。」 |
| 回帰のテスト | `SessionManager` の単体テストに、猶予の間の取り消し・猶予の後の取り消し・猶予が終わったときの内部の取り消し・猶予の間のほかの操作（確定・一時停止）・猶予の間の API の開始を追加する。`UiController` の単体テストに猶予の間の再起動・終了を追加する。`start_local_session` の単体テスト（断った理由ごとの detail）と、処理中のダイアログの結合テスト（終了の処理中の本文）を追加する | 猶予の経過は、`SessionDeps.now` と猶予の終わりを知らせるタイマーを差し替えて決定的に起こす |
