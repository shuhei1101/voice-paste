# 目的と制約

## 問いと答え

| 問い | 判断基準 | 答え | 補足 |
| --- | --- | --- | --- |
| 何を解決するための刷新か | 目的を 1 つに絞り、他の目的は順位を付けて並べる | 目的 1（最優先）: 録音・区切り（今の無音での区間の区切り）・文字起こし・用語の補正を、ほかのシステムから呼べる API として取り出す<br>目的 2: 出力先・文字起こしのエンジン・設定を、1 か所の追加・差し替えで変えられるようにする<br>目的 3: 画面の見た目・画面構成・メニューの並びを整える | 目的 1 は [#1](https://github.com/shuhei1101/voice-paste/issues/1) の中心で、[リスクと技術的負債](https://github.com/shuhei1101/voice-paste/blob/develop/dev/pr/10/%E3%83%AA%E3%82%B9%E3%82%AF%E3%81%A8%E6%8A%80%E8%A1%93%E7%9A%84%E8%B2%A0%E5%82%B5.md)の 1 行目（`main.py` に文字起こしだけを取り出す境界が無い）を解く。目的 2 は同じ一覧の `settings_gui.py`・`gui.py`・`transcribable.py` の負債を、目的 3 は tkinter の直書きの色・設定画面の並び・トレイのメニューの負債を解く。ライブラリを新しくすること自体は目的に置かない。画面のライブラリと画面構成は構造の決定（`4_構造の決定.md`）で見直す |
| 困っている変更の具体例は何か | 直近で実際に手間取った変更を、変更の内容と掛かった手間で書く | ・pycaw の版で API が変わり、録音中の音量の下げ戻しを 3 つの修正 commit（[b999285](https://github.com/shuhei1101/voice-paste/commit/b999285)・[78fcb97](https://github.com/shuhei1101/voice-paste/commit/78fcb97)・[25fdfc9](https://github.com/shuhei1101/voice-paste/commit/25fdfc9)、PR #15）で追従させた<br>・ローカルの Whisper の CUDA のクラッシュを、ワーカースレッドへの固定（[61f6437](https://github.com/shuhei1101/voice-paste/commit/61f6437)）と子プロセスへの隔離（[9413a98](https://github.com/shuhei1101/voice-paste/commit/9413a98)）の 2 度作り替えた<br>・AI 送信の送り先を 1 つ足す（[ccc3427](https://github.com/shuhei1101/voice-paste/commit/ccc3427)）のに、設定画面で欄の変数・画面の組み立て・入力の読み取り・`.env` への書き込みの 4 か所へ同じ手順を足した | commit の履歴と、リスクと技術的負債の一覧から拾った。掛かった時間の体感は書かない |
| システムの外の手作業は何か | コードに現れない手作業（デプロイ・データの修正・確認）を、頻度と担当者つきで書く | ・master を取り込んで `voice-paste.bat` から起動し直す（変更を入れるたび・ユーザー）<br>・設定画面に無い設定（Whisper の細かい設定・履歴・常駐モード）を `.env` に直に書く（設定を変えるとき・ユーザー）<br>・落ちたときにログを開いて原因を調べる（不具合のたび・ユーザー） | 頻度は書かない。測れる値は PoC で測る |
| 問題にどう気づくか | 検知の手段（アラート・問い合わせ・目視）を書き、手段が無い問題は「無い」と書く | 普段使いの中での目視（貼り付かない・音量が戻らない・画面が前に出ない）。起動時に文字起こしのエンジンを準備できない失敗と、前日までのログ（`voice-paste.bat` が起動のたびに消す）で分かる失敗は、気づく手段が無い | リスクと技術的負債の一覧の、起動の失敗とログの削除の行 |
| 成功の基準は何か | 刷新の前後で比べられる値か、観測できる状態で書く | ・ほかのプロセスが API で録音を開始・停止・完了でき、起こした文字を受け取れる<br>・ホットキーで録って貼り付ける今の使い方が、同じ操作で新しい構成の上で動き、話し終えてから貼り付くまでの時間が今より延びない<br>・出力先を 1 つ足す変更が、出力先のモジュールの追加と設定の追加で済む | 時間の目標値は品質目標（`2_品質目標.md`）で決め、PoC で測る |
| 終わりの定義は何か | 旧システムを止める条件を、観測できる状態で書く | Windows のショートカットの起動先が新しい構成に切り替わって master に入り、旧い処理の流れ（`main.py` の一続きの流れ・旧い設定画面）と配布用のビルドの仕組みのコードが消えている | 移行のために置いた一時的な仕組み（新旧の切り替え）も同時に消す |
| 刷新中に新機能を足すか | 足す / 足さないのどちらかで答え、足すなら対象を書く | 足さない | API そのものは刷新の目的のため新機能に数えない。刷新はホットキーで 1 回録る今の使い方と、API から録音を開始・停止・完了して呼び出し元が指定したエンドポイントへ起こした文字を返す使い方までとする。連続して録音し無音で区切って順に渡す使い方（[#1](https://github.com/shuhei1101/voice-paste/issues/1) の草案）と [#5](https://github.com/shuhei1101/voice-paste/issues/5)（設定したエンドポイントへ送る）は、API ができた後に足す。[#4](https://github.com/shuhei1101/voice-paste/issues/4) の最前面の維持は新機能ではなく、画面の作り直しの中で入れる |

## 制約

| 制約 | 種別 | 外せるか | 補足 |
| --- | --- | --- | --- |
| 録音・貼り付け・システム音量の操作は、ユーザーの Windows の端末で行う | 外せない | - | マイク・クリップボード・キー入力・音量は端末の OS の機能で、API を別に出しても端末側に残る |
| ローカルの Whisper を GPU で動かすには NVIDIA の GPU と CUDA 12・cuDNN 9 が要る | 外せない | - | faster-whisper の依存 |
| OpenAI API へ送れる音声は 25 MB まで・キーと料金は相手側で決まる | 外せない | - | 外部 API の仕様 |
| 開発・運用・利用を 1 人で行う | 外せない | - | 個人の道具 |
| 刷新の間も master を普段使いし続け、master へは E2E を通ったものだけを入れる | 自分で課した | 外せない | 普段使いの道具を止められない。連絡ボード「master は普段使いしている」 |
| Windows のショートカットから起動できる | 自分で課した | 外せない | 手段はバッチファイルに限らない。ショートカットで常駐のサーバーを起動し、その後はホットキーか API から音声入力を始める |
| ビルドせず、master のソースをそのまま動かす | 自分で課した | 外せない | 配布用のビルド（PyInstaller・`setup/build_exe.bat`）はやめてよい |
| Python で書く | 自分で課した | 外せない | faster-whisper・sounddevice などの資産が Python にあり、1 人で別の言語へ書き直す量に見合う利点が無い |
| 画面を tkinter、音量の操作を pycaw と comtypes、設定を python-dotenv の `.env` で持つ | 自分で課した | 外せる | 外すと、見た目をそろえる仕組み・版の追従の減少・構造を持てる設定が得られる。置き換え先は構造の決定（`4_構造の決定.md`）で決める |

## 調べたこと

| 題材 | 分かったこと | 出典 | 補足 |
| --- | --- | --- | --- |
| Kill It with Fire の 4 つの問い | 刷新の最初の 2 手は、刷新が生む価値と、その価値を見る指標を決めること。新しい技術だから移るのではなく、旧システムを仕様とみなさず、書き直しに機能を足しがちな点に気をつける | [InfoQ の著者インタビュー](https://www.infoq.com/articles/modernize-maintain-future-proof-systems)・[見本の第 2 章](https://nostarch.com/download/samples/KIWF_SampleCh2.pdf) | 目的からライブラリの刷新を外し、刷新中は機能を足さない答えの根拠。第 3・5・9 章の本文は読めず、見出しまで確かめた |
| Legacy Displacement の目的 | 刷新はまず欲しい成果（変更の費用を下げる・旧システムを退役させる 等）を決め、旧版と同じ機能をそろえること（Feature Parity）を目的にしない。移行のための一時的な仕組みは目的を果たしたら消す | [Patterns of Legacy Displacement](https://martinfowler.com/articles/patterns-legacy-displacement/)・[Feature Parity](https://martinfowler.com/articles/patterns-legacy-displacement/feature-parity.html)・[Transitional Architecture](https://martinfowler.com/articles/patterns-legacy-displacement/transitional-architecture.html) | 成功の基準を成果で書き、終わりの定義に一時的な仕組みの撤去を含めた根拠 |
| arc42 の制約 | 制約は設計の自由を狭める要求で、技術・組織・規約に分けて表にする。不利な制約は交渉してよい | [arc42 Section 2](https://docs.arc42.org/section-2/)・[arc42 FAQ C-2-4](https://faq.arc42.org/questions/C-2-4/) | 外せるかの列を「交渉できるか」として埋めた |
