# 要件

## 要望

テスト実行方法の層ごとに実行場所（`location`）を決めて記載し、`runner` の層を GitHub Actions の workflow で回せるようにする。

- 層ごとに、判定フローチャート『テストの実行場所』で `runner` / `local` を決める。lint の層は `local` にする
- `runner` の層は、workflow のインターフェース定義（起動契機は `workflow_dispatch`）のレビューに合格してから、`.github/workflows/` の workflow と `run_runner` を記載する
- `runner` の層も `run_all`・`run_one` を手元のコマンドとして残し、ランナーで回せないとき（無料枠の使い切り・GitHub の障害）に手元で回せる状態を保つ
- 層の中の一部のテストだけが手元でしか用意できないものを使用する場合は、そのテストにマーカーを付け、ランナーの全件実行から除く。手元の全件実行はマーカーによらず全件を回す
- ジョブのタイムアウトは判定フローチャート『タイムアウトの決め方』で決める
- lint の層の全件実行に actionlint を加える

workflow は develop に入るまで `workflow_dispatch` で起動できないため、この作業 PR の全件実行は手元で回し、回せなかった理由をログに記載する。

`未確定`: ランナーの OS（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `windows-latest` で回す | 手元の全件実行（Windows の `.venv/Scripts/python.exe`）と同じ OS で、skip するテストが一致する | Linux でだけ実行するテスト（Linux の単一インスタンス等）はランナーでも skip のまま |
| B | `ubuntu-latest` で回す | 起動が速い | Win32 に依存するテストが skip になり、手元と skip の件数が一致しない |
| C | 両方を `strategy: matrix` で回す | OS ごとのテストを両方実行できる | ジョブが倍になる |

推奨: A

手元の全件実行と skip の件数を比べる確認（判定フローチャート『テストの実行場所』の ※4）が、同じ OS でないと成り立たないため。

`未確定`: workflow の分け方（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 1 つの workflow（`test.yml`）が入力 `layer` で回す層を選ぶ | uv と依存の導入の step を 1 か所で持てる。テンプレート『テスト実行方法』の例と同じ構造 | 層ごとに要る道具が違うと、step の条件分岐が増える |
| B | 層ごとに workflow を分ける | 層ごとの step が単純になる | 道具の導入の step が workflow ごとに重複する |

推奨: A

`runner` の候補の層（単体・結合）は、どちらも uv と pytest で回り、共通の step が大半を占めるため。

`未確定`: workflow を持つ対象システム（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | アーキテクチャ図の `subsystems` に `CI` を追加し、workflow とそのインターフェース定義をそこに属させる | workflow の属するサブシステムと、計画書の名前が決定する | アーキテクチャ図の変更が加わる |
| B | アーキテクチャ図の `repository.notes` にだけ記載し、サブシステムにしない | 変更が小さい | workflow の属するサブシステムが決定しない |

推奨: A

作業 PR の計画書と設計書の分類は、アーキテクチャ図のサブシステムの名前で分けるため。
