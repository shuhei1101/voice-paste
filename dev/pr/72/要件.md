# 要件

## 要望

単一ユースケース「常駐アプリを起動する」の E2E の `test_error_when_engine_unavailable`・`test_error_when_api_unavailable` が、シナリオの期待値「トレイで起動に失敗したことが知らされている」「トレイで API を使えないことが知らされている」を確かめて pass する。

- 先に、起動の失敗・API を使えない知らせの Windows の通知（`QSystemTrayIcon.showMessage`）が画面に出ているか（トーストが表示されたか）を実機で確かめる
- 通知が画面に出ている場合、E2E の確かめをシナリオの範囲（知らせを出したこと）に合わせ、通知センターに残っているかを確かめない
- 通知が画面に出ていない場合、常駐アプリの不具合として通知を出るように直し、起点 Issue を `type:bug` に書き直す
- `test_error_when_engine_unavailable` も、`test_error_when_api_unavailable` と同じく知らせの種類（`engine_unavailable`）を確かめる
- 2 件が、release PR [#52](https://github.com/shuhei1101/voice-paste/pull/52) の E2E の全件の実行で pass する

`未確定`: 通知が画面に出たことの E2E での確かめ方（決める段: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 常駐アプリのログの「ユーザーへの知らせ（{種類}…）」（`AppDriver.notified`）で確かめる | 画面の状態に左右されず、毎回同じ結果になる | 通知が画面に出たことまでは確かめない |
| B | 通知のトーストを UI Automation で探し、見出しを読んで確かめる | 利用者に見える通知まで確かめる | トーストは数秒で畳まれ、集中モード・通知の設定で出ないことがあり、結果が揺れる |

推奨: A

シナリオの期待値は「トレイで知らされている」で、通知を出す処理（見出し・本文）は結合テスト `tests/integration/ui/test_tray_notification.py` が確かめている。
画面に出るかは、この PR の切り分けで一度実機で確かめれば足りる。

`未確定`: 画面設計『トレイの通知』の「通知センターに残る」の扱い（決める段: 画面設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 切り分けで通知センターに残ると分かれば、記述をそのまま保つ | 設計を変えない | - |
| B | 切り分けで、venv の `python.exe` から出した通知が通知センターに残らないと分かれば、残るかを利用者の環境（ビルドした exe）に依るものとして書き直す | 設計と実際の動きが合う | 利用者に見える振る舞いの記述が変わり、ユーザーの確認が要る |

推奨: 切り分けの結果に合わせて A か B を選ぶ

通知センターに残ることは、[#37](https://github.com/shuhei1101/voice-paste/pull/37) のモック作成でユーザーが決めた振る舞いのため、記述を変えるときはユーザーに確かめる。
